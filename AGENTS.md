# Работа с проектом

Лендинг частной практики Юрия Грачева: React, TypeScript, Vite, CSS Modules. Команды запуска и публикации описаны в [README.md](README.md).

## Код и содержимое

- Следуйте существующей структуре: секции в `src/sections`, функциональность в `src/features`, общие компоненты и утилиты в `src/shared`.
- Храните компонент, его CSS Module и данные рядом. Тексты секций выносите в `*.data.ts`, общие контакты — в `src/shared/config/contacts.ts`.
- Используйте переменные цветов и типографики из `src/app/styles/base.css`. Для обычной вёрстки достаточно существующего CSS; не добавляйте UI-библиотеку без необходимости.
- Сохраняйте адаптивные WebP, локальные шрифты и их лицензии. Не заменяйте исходные фотографии и тексты политики без запроса.
- Сохраняйте загрузку нижних секций через `DeferredSection`, переходы по якорям, управление с клавиатуры и поддержку `prefers-reduced-motion`.
- Метрика подключается только через `src/shared/lib/analytics/metrika.ts` после согласия на cookies. Не добавляйте второй HTML-сниппет или безусловный tracking-пиксель. Якоря внутри лендинга не считаются отдельными просмотрами.
- `.env.production` содержит только публичные настройки. Токены и другие секреты нельзя помещать в `VITE_*` или клиентский код.

## Проверки

- Перед изменениями прочитайте состояние Git и затрагиваемый код; сохраняйте чужие незавершённые изменения.
- После исправления бага просмотрите diff и 5–10 связанных файлов. Сверяйтесь с принятыми в проекте подходами; проверяйте необычные имена и конструкции поиском по проекту.
- Убирайте ненужные приведения типов, избыточные аннотации и неясные имена в пределах задачи. Не совмещайте задачу с посторонней уборкой.
- После изменения кода запускайте `npm run verify`. Добавляйте тесты для существенного поведения и исправленных ошибок, а не для повторения реализации. Для изменений только в документации достаточно Prettier и `git diff --check`.
- Изменения вёрстки проверяйте в браузере на 320, 390 и 1440 px; при изменении адаптивности — также на 360, 375, 420 px и около затронутых брейкпоинтов. DOM-тесты не подтверждают геометрию.
- Исходный макет Figma: файл `AumZQjdN1iRhewiyxXV7xw`, фреймы `239:168` (320), `3:2` (390), `4:2` (1440). Не заявляйте сверку с макетом без фактического сравнения.

## Работа с пользователем и публикация

- Вопросы по реализации во время работы отвечайте кратко и продолжайте задачу. Останавливайтесь, если пользователь явно просит остановиться или меняет направление.
- Коммит, push и публикацию выполняйте по явному запросу пользователя. Уже полученное разрешение действует в рамках задачи; повторно его не запрашивайте без изменения обстоятельств. Просьба остановить публикацию отменяет разрешение на неё.
- Перед push проверьте remote и права доступа; используйте настроенную Git-идентичность пользователя. Не включайте в коммит посторонние изменения.
- «Фулл-цикл» означает реализацию, ревью diff, проверки, коммит и push с отслеживанием CI. Слияние и деплой требуют отдельного запроса.
- Деплой запускается вручную из `main` через `.github/workflows/deploy.yml`. Не включайте автоматическую публикацию при push без запроса.
- После разрешённой публикации проверьте Actions, DNS, HTTPS и доступность страниц. Различайте успешную сборку, завершённый деплой и доступность домена; сообщайте о фактическом результате и оставшихся препятствиях.
